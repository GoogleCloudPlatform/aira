## Background & Security Finding

A security review identified an unauthenticated arbitrary Looker user-deletion vulnerability in `src/Backend/src/api/routers/auth/endpoints.py` (mounted under `/api/v1/auth` in `src/Backend/src/api/factory.py:61`) paired with an unwired legacy feeder route:

- **`POST /api/v1/auth/user/looker/_handle`** (`src/Backend/src/api/routers/auth/endpoints.py:182-194`, handler `handle_delete_users_pubsub`): Declares **no** `fastapi.Security` dependency on a Cloud Run service deployed with `--allow-unauthenticated` (`src/Backend/cloudbuild.yaml:52`). It validates `PubsubRequest` (`src/Backend/src/api/routers/schemas.py:17-23`), base64-decodes `body.message.data`, parses `user_id` via `PubsubDeleteUserData` (`src/Backend/src/api/routers/auth/schemas.py:73-78`), and calls `LookerDashboard.delete_looker_user(data.user_id)` (`src/Backend/src/api/adapters/google/looker.py:173-178`), which invokes `self._looker.delete_user(user_id)`. Because `self._looker = looker_sdk.init40()` (`looker.py:71`) authenticates to Looker's REST API 4.0 using admin API3 credentials (`LOOKERSDK_BASE_URL`, `LOOKERSDK_CLIENT_ID`, `LOOKERSDK_CLIENT_SECRET` mounted from Secret Manager in `src/Backend/cloudbuild.yaml:50`), and Looker's `DELETE /users/{user_id}` endpoint permanently deletes **any** Looker user by ID (moving their reports, Looks, and dashboards to Trash, breaking public URLs, and deleting schedules and alerts, restricted only by *"The user cannot delete themselves. The last administrator user cannot be deleted."*), any unauthenticated internet caller can delete non-embed Looker users and administrators by POSTing `{"message":{"data":"eyJ1c2VyX2lkIjoiMSJ9","messageId":"1"},"subscription":"sub"}`.
- **`GET /api/v1/auth/users/looker`** (`src/Backend/src/api/routers/auth/endpoints.py:158-179`, handler `set_delete_users_pubsub`): Lists Looker embed users via `LookerDashboard.get_all_looker_users()` (`looker.py:180-184`, `search_users(embed_user=True)`) and publishes `DeleteLookerUserMessage` (`auth/schemas.py:64-70`) to `settings.get("pubsub_delete_user_topic")`. Neither the `delete-looker-user-queue` Pub/Sub topic/push subscription nor any Cloud Scheduler trigger exists anywhere in `src/IAC/06-message_service.tf`, and `_PUBSUB_DELETE_USER_TOPIC` is unset in `src/Backend/cloudbuild.yaml` and `src/Backend/env.example`. Worse, because `MessagePublisher.publish` (`src/Backend/src/api/adapters/google/pubsub.py:31-36`) falls back to `self.topic_path` (`_PUBSUB_TOPIC` / `processor_queue`) when `topic` is `None` or empty, invoking `GET /api/v1/auth/users/looker` in production would publish malformed `{"user_id": ...}` messages onto the student exam audio-processing queue.

## Technical Decisions & Source-Verified Rationale

1. **Delete Outright Rather Than Authenticate the Pub/Sub Push Endpoint**
   - Per Google Cloud Pub/Sub push authentication documentation, securing a push endpoint on a public Cloud Run service requires configuring an OIDC push service account on the subscription and verifying the `Authorization` Bearer JWT (or enforcing Cloud Run IAM Invoker checks), plus provisioning the missing Pub/Sub topic, push subscription, and Cloud Scheduler job in `src/IAC/06-message_service.tf` and `_PUBSUB_DELETE_USER_TOPIC` in `src/Backend/cloudbuild.yaml`.
   - Even if gated, `LookerDashboard.delete_looker_user(user_id)` calls `self._looker.delete_user(user_id)` (`DELETE /users/{user_id}`), which Looker's API 4.0 reference documents as an irreversible user deletion (**"This action cannot be undone."**) with no `embed_user` restriction—continuing to mount Looker Admin API3 credentials (`LOOKERSDK_CLIENT_ID` / `LOOKERSDK_CLIENT_SECRET`) into the public Backend container leaves unnecessary blast radius.
   - `src/Frontend/` and `src/Agent/` have zero references to `/auth/users/looker` or `/auth/user/looker/_handle`; removing both endpoints and `looker-sdk` eliminates the vulnerability and enforces least privilege by removing Looker Admin REST credentials from the Backend runtime altogether.

2. **`looker-sdk` Is Unused by Looker Signed SSO Embedding—and Eagerly Raises `SDKError` Without `LOOKERSDK_BASE_URL`**
   - **Frontend/Backend Signed SSO contract (`@looker/embed-sdk` `^1.8.5`):** `src/Frontend/src/libs/looker/looker.ts:11-15` initializes `LookerEmbedSDK.init(NEXT_PUBLIC_LOOKER, { url: "${NEXT_PUBLIC_API_URL}${ENDPOINT_AUTH_LOOKER}", headers: [{ name: "Authorization", value: "Bearer ..." }], withCredentials: true })`. Per `@looker/embed-sdk`'s *Signed URL Auth Endpoint* documentation and reference helper (`server_utils/auth_utils.py`), signed embedding only calls `GET <auth.url>?src=...` expecting JSON `{ url }` (`dict[str, str]` `{"url": response}` at `auth/endpoints.py:103,111`) and explicitly notes: *"Manual URL generation and signing avoids calling the Looker API"*.
   - **Direct `auth_utils.py` provenance of `LookerDashboard`:** Comparing `src/Backend/src/api/adapters/google/looker.py:25-171` against upstream `looker-open-source/embed-sdk/master/server_utils/auth_utils.py` confirms `User` (`looker.py:25-59`) and `LookerDashboard.{_sign,_to_string,get_signed_url}` (`looker.py:61-171`, folding upstream `Looker` into `LookerDashboard`) are a direct Python 3 port of `auth_utils.py` (`hmac.new(..., sha1)` + `base64.b64encode` over the exact 12-line newline-delimited `string_to_sign` using `_LOOKER_HOST` and `_LOOKER_SECRET` from `GoogleModule.provide_looker` at `dependencies.py:674-681` and `InternetlessModule.provide_looker` at `dependencies.py:795-802`), with zero `looker_sdk` usage.
   - **Eager `init40()` failure mode (`looker-sdk` `24.20.0`):** Installed `looker_sdk/__init__.py:48-65` shows `looker_sdk.init40()` instantiates `ApiSettings` (`looker_sdk/rtl/api_settings.py:62-106`, reading `looker.ini` and `LOOKERSDK_BASE_URL` / `LOOKERSDK_VERIFY_SSL` / `LOOKERSDK_TIMEOUT` / `LOOKERSDK_CLIENT_ID` / `LOOKERSDK_CLIENT_SECRET`) and **immediately calls `settings.is_configured()`** (`__init__.py:57` and `AuthSession.__init__` at `auth_session.py:50`) before returning the client. In `looker_sdk/rtl/transport.py:65-67`, `PTransportSettings.is_configured()` raises `error.SDKError("Missing required configuration value: base_url")` whenever `looker.ini` is absent and `LOOKERSDK_BASE_URL` is unset or empty (whereas `client_id` / `client_secret` validation in `AuthSession._login` at `auth_session.py:132-136` is deferred until the first HTTP call). Removing `self._looker = looker_sdk.init40()` makes `LookerDashboard(looker_host, looker_secret)` pure stdlib initialization with zero `LOOKERSDK_*` or `looker.ini` requirement.

3. **Exact Post-Deletion Routing, `fastapi-pagination`, & OpenAPI Behavior (`Starlette 0.41.3` + `FastAPI 0.115.6`)**
   - **`POST /api/v1/auth/user/looker/_handle` & `GET /api/v1/auth/users/looker` -> `404 Not Found`:** After deleting both handlers, `auth_router` (`src/Backend/src/api/routers/auth/endpoints.py`) retains exactly five literal routes: `POST /token` (`L28`), `POST /refresh` (`L60`), `GET /dashboard` (`L96`), `POST /forgot` (`L114`), and `POST /reset` (`L141`). Neither `auth_router` (`/api/v1/auth`) nor `base_router` (`/api/v1`, which only defines `GET /healthz` at `src/Backend/src/api/routers/endpoints.py:14`) declares any parameterized path segments that could partially match `/auth/user/looker/_handle` or `/auth/users/looker`. Per Starlette `0.41.3` `Router.app` (`starlette/routing.py:716-765`), every registered route returns `Match.NONE`, `partial` stays `None`, `redirect_slashes` (`L750-763`) finds no slash-toggled match, and `await self.default(scope, receive, send)` returns `404 Not Found` (`{"detail": "Not Found"}`) across all HTTP methods without `405` or `307` behavior.
   - **`fastapi_pagination.add_pagination(app)` (`0.12.34`):** Installed `fastapi_pagination/api.py:359-406` iterates `parent.routes` and returns immediately unless `route.response_model` is a subclass of `AbstractPage`; neither the removed `-> fastapi.Response` routes nor retained `GET /api/v1/auth/dashboard` (`-> dict[str, str]`) is affected.
   - **OpenAPI schema collection (`fastapi/openapi/utils.py:425-453`):** FastAPI `0.115.6` `get_fields_from_routes` collects `components.schemas` models exclusively from routes where `getattr(route, "include_in_schema", None)` is truthy (`utils.py:432-435`). Because `processor_router` (`src/Backend/src/api/routers/processor/endpoints.py:27`, handlers at `L155-158` and `L359-362`) sets `include_in_schema=False` on the entire router and `knowledge_base_router`'s `/process-message` (`src/Backend/src/api/routers/knowledge_base/endpoints.py:335-337`) also sets `include_in_schema=False`, `POST /api/v1/auth/user/looker/_handle` (`auth/endpoints.py:182-185`) was the **sole** `include_in_schema=True` route exposing `PubsubRequest` and `PubsubMessage` in `/openapi.json` (`PubsubDeleteUserData` was parsed imperatively via `.parse_raw(...)` and `DeleteLookerUserMessage` was a stdlib `@dataclasses.dataclass`, so neither was ever in `components.schemas`). Deleting the two Looker routes removes `/api/v1/auth/user/looker/_handle` and `/api/v1/auth/users/looker` from `/openapi.json` `paths` and removes `PubsubRequest` and `PubsubMessage` from `/openapi.json` `components.schemas`—reducing public schema disclosure of internal Pub/Sub push structures while keeping `api.routers.schemas.{PubsubRequest,PubsubMessage}` intact at runtime.

4. **Preserve Shared Scheduler Auth & Pub/Sub Envelope Schemas**
   - `auth.validate_scheduler_token` (`src/Backend/src/api/helpers/auth.py:82-98`) remains actively used by `GET /api/v1/processor/sync` (`src/Backend/src/api/routers/processor/endpoints.py:514`) and must not be removed.

5. **Cloud Build Secret Unmounting (`--remove-secrets` + `--update-secrets` on Existing & Greenfield Environments) & Poetry 2.x Dependency Pruning**
   - **Terraform Secret Manager preservation:** Leaving `lookersdk_base_url`, `lookersdk_client_id`, and `lookersdk_client_secret` intact in `src/IAC/10-Secrets.tf:344-435` (along with project-level Secret Manager IAM in `src/IAC/02-sa_and_iam.tf:79-103`) avoids destructive Secret Manager deletions and preserves secret availability if an operator rolls Cloud Run back to a prior revision.
   - **`gcloud run deploy` flag mutex, execution order, & greenfield bootstrap safety:** Google Cloud SDK's `gcloud run deploy` reference explicitly documents that *"Only `--update-secrets` and `--remove-secrets` can be used together. If both are specified, `--remove-secrets` will be applied first."* Furthermore, Google Cloud SDK's `SecretEnvVarChanges` (`googlecloudsdk/command_lib/run/config_changes.py:776-787`, `_PruneMapping`: `if var_or_path in mapping: del mapping[var_or_path]`) and v2 `AdjustContainer` (`googlecloudsdk/command_lib/run/v2/config_changes.py:819-835`, `if env_var.name in self.removes: continue`) guard secret removal by membership in the container's current secret map. Pairing `--remove-secrets=LOOKERSDK_BASE_URL,LOOKERSDK_CLIENT_ID,LOOKERSDK_CLIENT_SECRET` with `--update-secrets=...` in `src/Backend/cloudbuild.yaml:50` therefore works both when **wrapping brand-new environments** (silent no-op on empty secret map before adding the 10 Backend secrets) and when **updating existing environments** (actively unmounting `LOOKERSDK_*` without `clear_others=True` wiping any operator-added secrets).
   - **Poetry 2.x lockfile pruning:** `src/Backend/poetry.lock:6134` uses `lock-version = "2.1"`. Running `poetry remove looker-sdk` removes `looker-sdk` from `pyproject.toml:52` and prunes `looker-sdk` (`24.20.0`) plus its only unshared transitive dependency `cattrs` (`24.1.2`) while leaving `attrs`, `requests`, `typing-extensions`, and `urllib3` intact for other locked packages (`pytest`, `google-api-core`, `chromadb`, etc.).

6. **Test DI Wiring (`TestGoogleModule`), `HTTPBearer` `403` vs. `401`, `GetSession` Eager Loading, & Stale `user.county` Attribute**
   - **Request-time `fastapi-injector` resolution + `injector` `auto_bind=True` hazard:** In `fastapi-injector` `0.6.2` (`fastapi_injector/injected.py:11-20`), `Injected(ports.Dashboard)` returns `Depends(inject_into_route)`, resolving `get_injector_instance(conn.app).get(ports.Dashboard)` per request (`L17-18`) rather than at `create_app()` startup. In `injector` `0.20.1` (`injector/__init__.py:403,645-648,865-870`), `Injector` defaults to `auto_bind=True`: because `TestGoogleModule` (`src/Backend/tests/conftest.py:164-186`) currently omits a provider for `ports.Dashboard` (`abc.ABC`), hitting `GET /api/v1/auth/dashboard` in tests would cause `Binder.get_binding` to auto-bind `ports.Dashboard` to itself and fail with `TypeError: Can't instantiate abstract class Dashboard...`. Adding `@injector.provider @injector.singleton def provide_looker(self) -> ports.Dashboard` returning `looker.LookerDashboard(looker_host="looker.example.com", looker_secret="test-looker-secret")` in `TestGoogleModule` wires the real adapter with zero external calls.
   - **`HTTPBearer` `403` vs. `auth.get_token` `401`:** In FastAPI `0.115.6` (`fastapi/security/http.py:301-321`), `HTTPBearer(auto_error=True)` raises `HTTPException(status_code=HTTP_403_FORBIDDEN, detail="Not authenticated")` (`L308-310`) when `Authorization` is missing/empty and `"Invalid authentication credentials"` (`L316-318`) when `Authorization` uses a non-`Bearer` scheme, whereas a syntactically valid `Authorization: Bearer <forged>` header passes `HTTPBearer` and raises `errors.TokenExpired()` (`401` `{"code": "token_expired_or_invalid", ...}`) inside `auth.get_token` (`helpers/auth.py:117-124`).
   - **SQLAlchemy `2.0.37` `joinedload` + `Result.unique()` in `GetSession`:** `GetSession.__call__` (`src/Backend/src/api/adapters/sqlalchemy/session_query.py:98-120`) loads `models.Session.user` with `joinedload(models.User.groups)` (+ `Group.organization`) and `joinedload(models.User.organizations)` and applies `.unique()` (`L117`) as required by SQLAlchemy 2.0 for collection joins (while `User.role` uses `lazy="joined"` on `models/users.py:130-134`).    - **Pre-existing `user.county` crash in `LookerDashboard.get_signed_url` (`looker.py:109`):** Migration `80dc3596cd72` (`src/Backend/migrations/versions/2026_04_30_002357-80dc3596cd72_drop_county_columns.py:22`) dropped `users.county` and removed `county` from `models.User` (`src/Backend/src/api/models/users.py:110-116`), but `LookerDashboard.get_signed_url` (`looker.py:109`) still evaluates `"county": user.county`. ## Surfaced Conflicts Between Official Docs & Existing Code

1. **Cloud Run `gcloud run deploy --update-secrets` Merge Semantics (Official Docs) vs. Omitting Keys From `--update-secrets` (`src/Backend/cloudbuild.yaml:50`)**
   - **Official docs & `gcloud` CLI source:** `--update-secrets` incrementally adds or updates specified secret bindings while retaining previously configured secrets on an existing Cloud Run service; removing specific mounted secret environment variables without `clear_others=True` wiping out-of-band secrets requires `--remove-secrets=[KEY,...]`, which `gcloud run deploy` explicitly allows alongside `--update-secrets` (applied first) and implements as a membership-checked no-op (`if var_or_path in mapping`) on brand-new services (`googlecloudsdk/command_lib/run/config_changes.py:776-787`, `v2/config_changes.py:819-835`).
   - **Existing codebase:** `src/Backend/cloudbuild.yaml:50` uses `--update-secrets=...` and is used both for updating existing environments and bootstrapping new ones.
   - **Selected approach:** Remove `LOOKERSDK_BASE_URL=lookersdk_base_url:latest`, `LOOKERSDK_CLIENT_ID=lookersdk_client_id:latest`, and `LOOKERSDK_CLIENT_SECRET=lookersdk_client_secret:latest` from `--update-secrets` **and** add `--remove-secrets=LOOKERSDK_BASE_URL,LOOKERSDK_CLIENT_ID,LOOKERSDK_CLIENT_SECRET` in `src/Backend/cloudbuild.yaml:50`.

2. **Looker Signed SSO `string_to_sign` Optional `ca_chat` Parameter (Current Looker Docs) vs. 12-Line `auth_utils.py` Signature in `LookerDashboard._sign` (`src/Backend/src/api/adapters/google/looker.py:120-135`)**
   - **Official Looker docs vs. upstream `embed-sdk/server_utils/auth_utils.py`:** Current Looker Signed SSO Embedding documentation includes a 13th trailing parameter (`ca_chat` for Conversational Analytics dashboard data agent visibility) when Conversational Analytics is used, whereas Looker's `embed-sdk/server_utils/auth_utils.py` signs the classic 12-field newline-delimited payload with `hmac.new(..., sha1)`.
   - **Existing codebase:** `LookerDashboard._sign` (`looker.py:120-140`) implements the exact 12-field `embed-sdk/server_utils/auth_utils.py` payload and does not pass `ca_chat`.
   - **Selected approach:** Per confirmed scope, keep `LookerDashboard._sign` and `_to_string` URL-signing logic strictly unchanged so existing Looker embed configurations are not altered, modifying only `getattr(user, "county", None)` at `looker.py:109` and removing the `looker_sdk` client/methods.

3. **Poetry 2.x Lockfile CLI (`poetry remove` / `poetry lock`) vs. Removed Poetry 1.x `--no-update` Flag**
   - **Official Poetry 2.x docs:** `poetry lock` preserves existing locked package versions by default (`--regenerate` replaces the lockfile from scratch, and Poetry 1.x's `--no-update` flag no longer exists in Poetry 2.x).
   - **Existing codebase & tooling:** `src/Backend/poetry.lock:6134` is `lock-version = "2.1"` (Poetry `2.3.4` locally; `POETRY_VERSION=2.0.1` in `src/Backend/Dockerfile:8`).
   - **Selected approach:** Run `poetry remove looker-sdk` (followed by `poetry check --lock`) rather than manual `pyproject.toml` edits paired with removed Poetry 1.x flags.

4. **`@pytest.mark.asyncio` (`pytest-asyncio` `0.23.8` Strict Mode in Repo) & `ASGITransport` (`httpx` `0.27.2`) vs. `@pytest.mark.anyio` (FastAPI Docs Default) & `AsyncClient(app=...)` (`tests/conftest.py:317`)**
   - **Official docs:** FastAPI's *Async Tests* guide uses `@pytest.mark.anyio` with `AsyncClient(transport=ASGITransport(app=app), base_url="http://test")`, whereas `pytest-asyncio` `0.23.8` strict mode only runs tests marked with `@pytest.mark.asyncio` and async fixtures decorated with `@pytest_asyncio.fixture`.
   - **Existing codebase:** `src/Backend/pyproject.toml:119` sets `asyncio_mode = "strict"`, `tests/conftest.py:189-211` binds DB/app fixtures to a session-scoped `asyncio` `event_loop`, and `tests/conftest.py:324-338` already provides `unauthenticated_client` using `httpx.ASGITransport(app=test_app)`.
   - **Selected approach:** Decorate all async regression tests with `@pytest.mark.asyncio`, reuse the existing `unauthenticated_client` and `client` fixtures in separate test functions, and avoid `@pytest.mark.anyio`.
